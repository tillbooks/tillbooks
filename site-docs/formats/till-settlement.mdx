---
title: "Settlement files (till-settlement/v1)"
description: "An open format for the money a payment processor or a marketplace holds for you, and how TILL books it."
---

A payment processor, a marketplace or a booking platform often collects money for you, keeps it in a
balance for a while, takes its fees, pays part of it to third parties and then sends the rest to your
bank. Your bank statement only shows that last transfer. The sales, the refunds, the fees and the VAT
on them happened inside the processor's balance.

`till-settlement/v1` is an open JSON format for those events. Any system that holds such a balance can
write it. TILL reads it with `import_settlement` and books every event against a clearing account (a
Durchlaufkonto) through a booking template that you keep in TILL.

The file describes what happened. It never decides how you book it: the accounts and the tax codes
come from your template, not from the file.

## The file

```json
{
  "schema": "till-settlement/v1",
  "source": { "system": "your-platform", "processor": "your-processor", "entity": "Muster GmbH" },
  "generatedAt": "2026-08-01T06:00:00.000Z",
  "period": { "from": "2026-07-01", "to": "2026-07-31" },
  "currency": "CHF",
  "warnings": ["One transaction had no document number."],
  "events": [
    {
      "id": "sale-1001",
      "kind": "sale",
      "day": "2026-07-03",
      "currency": "CHF",
      "amount": 216.20,
      "net": 200.00,
      "vat": { "amount": 16.20, "code": "standard", "rate": 8.1 },
      "document": { "type": "client_invoice", "number": "R-0001" },
      "counterparty": "Lena Beispiel",
      "description": "Customer payment",
      "refs": { "chargeId": "ch_0001" }
    }
  ]
}
```

| Field | Required | Meaning |
| --- | --- | --- |
| `schema` | yes | Always `till-settlement/v1`. Any other value refuses the whole file. |
| `source.system` | yes | The platform that wrote the file. |
| `source.processor` | yes | The processor whose balance the events describe. |
| `source.entity`, `generatedAt`, `period`, `currency`, `clearingAccount`, `signConvention` | no | Kept for the reader. TILL books by none of them. |
| `warnings` | no | Texts the producer wants a person to see. TILL passes them through. |
| `events` | yes | The events, at most 20,000 per file. |

TILL matches `source.system` and `source.processor` without regard to case or surrounding spaces.

## An event

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | yes | The producer's own id, stable across files. TILL recognises an event it booked before by it. |
| `kind` | yes | One of the kinds below. |
| `day` | yes | The booking day, `YYYY-MM-DD`, in the company's own time zone. The entry is dated this day. |
| `currency` | yes | The workspace currency (CHF). |
| `amount` | yes | The effect on the processor balance, gross including VAT. Positive means money into the balance. |
| `net` | yes | The amount without VAT, with the same sign. |
| `vat` | no | `{ amount }` with the VAT, signed like `net`, or `null`. `code` and `rate` are the producer's labels and are not read. |
| `document` | no | `{ type, number }` of the invoice, credit note or self-bill behind the event. |
| `counterparty`, `description` | no | Texts for the entry. |
| `refs` | no | Any external references (up to 4 KB as JSON). TILL keeps them with the event. |

`amount` must equal `net + vat.amount` exactly. For a sale of 10.81 that is 10.00 plus 0.81; for a fee of
-1.08 it is -1.00 plus -0.08.

### Amounts

Write an amount as a JSON number (`10.81`) or a decimal string (`"10.81"`), with at most two decimal
places and a leading minus for a negative value. TILL reads the digits, not a floating-point value, so
`10.81` is exactly 1081 Rappen. Three decimal places, an exponent (`1e3`) or a plus sign are refused.

### Kinds

| Kind | What it is |
| --- | --- |
| `sale` | A customer paid. |
| `refund` | A customer got money back. |
| `processing_fee` | The fee the processor took on a payment. |
| `service_fee` | Any other fee the processor charged. |
| `third_party_payout` | Money passed on to someone else, for example a seller on a marketplace. |
| `third_party_payout_reversal` | Such a payout coming back. |
| `reserve` | Money the processor holds back or releases inside its balance. |
| `bank_payout` | A transfer from the balance to your bank account. |
| `bank_payout_summary` | A bank payout reported as one total line instead of itemised `bank_payout` events. Use one or the other for a payout, never both. |
| `other` | Anything else. |

## What TILL refuses

TILL refuses the whole file, and writes nothing, when:

- `schema` is not `till-settlement/v1`, `source` is incomplete, or `events` is missing;
- there is no booking template for the file's source;
- the file contains a kind the template does not map;
- the template names an account or a tax code that is no longer usable.

TILL refuses a single event, and books all the others, when:

| Code | Why |
| --- | --- |
| `missing_id` | The event has no id. |
| `duplicate_id` | Two events of the file share an id. Both are refused. |
| `invalid_day` | `day` is not a calendar date. |
| `currency_mismatch` | The event is not in the workspace currency. |
| `unknown_kind` | `kind` is not one of the kinds above. |
| `invalid_amount` | An amount is not an exact decimal with at most two places. |
| `amount_mismatch` | `amount` is not `net + vat.amount`. |
| `vat_not_exact` | The VAT is not what the tax code gives on the net or on the gross. |
| `vat_unmapped` | The event carries VAT, but the template books its kind without a tax code. |
| `event_amended` | An event with this id was booked before with other figures. |
| `period_locked` | The day falls into a locked or closed period. |
| `attachment_failed` | A PDF for the event could not be filed as its Beleg, so the event was not booked. |

Unknown fields are ignored, so a producer can add its own.

## The booking template

You set one template per source with `set_settlement_template`:

- the clearing account, a balance account that mirrors the processor balance;
- per kind, either `book` with the contra account and a tax code (or none), `skip`, or `attention`.

When you leave a kind out, it takes its default: `bank_payout` and `bank_payout_summary` skip, because
the bank import books the transfer (bank account against the clearing account); `reserve` skips,
because the money stays in the processor balance; `other` is `attention`, so a person looks at it. Any
other kind you leave out is unmapped, and a file that contains it is refused until you map it.

## How an event is booked

Each event of a kind the template books becomes one balanced entry, dated `day`:

| Account | Amount |
| --- | --- |
| Clearing account | `amount` (positive is Soll) |
| Contra account from the template | `-net`, with the template's tax code |
| VAT account (Umsatzsteuer or Vorsteuer) | `-vat.amount` |

The MWST-Abrechnung reads the VAT and the base the file states. TILL accepts the stated VAT when it is
what the tax code gives in one rounding step, on the net or on the gross; any other VAT is refused for
that event rather than booked a Rappen off.

An event with `"vat": null` under an input (Vorsteuer) code, for example a payout to a seller who is not
registered for VAT or a fee charged without tax, is booked without VAT: the gross goes to the contra
account with no tax code and no VAT line, because the file states no input VAT to deduct. One kind can
mix both, so a `third_party_payout` with VAT and one without book under the same template. A sale under
an output (Umsatzsteuer) code gets no such allowance: `"vat": null` there is checked like any stated VAT
and refused as `vat_not_exact` when the code owes tax on it.

The entry text is the description and the counterparty, and the document number is the entry's
reference. PDFs you send along (`attachments`, each with its `documentNumber`) are filed as Belege on
the entries with that document number. A PDF that cannot be filed on an event booked earlier leaves that
entry as it is: the event answers `already_imported` with the code `attachment_failed` and the reason.
Every PDF filed on no entry is listed in `unmatchedAttachments`.

## Importing again

TILL recognises every event it booked by the workspace, the source and the event's `id`. Importing the
same file again books nothing new: each event answers `already_imported`. An event with a known id and
other figures is refused as `event_amended`, and the entry already booked stays as it is. To correct it,
book a reversing entry.

## Checking the clearing account

The answer of `import_settlement` carries a reconciliation. Every figure comes from the file's own
events and the entries TILL booked for them, never from whatever else your clearing account carries
(another file, a manual entry, a bank line):

- `expectedClearingChangeMinor`: the sum of every event amount in the file, bank payouts included. This
  is how much the processor balance moved.
- `bookedClearingChangeMinor`: what the entries of the file's events put on the clearing account, whether
  they were booked by this import or an earlier one, net of any reversing entry you booked.
- `bankPayoutsMinor`: the bank payouts of the file that have no entry from the import. The bank import
  books them.
- `notBookedByImportMinor`: every other event without an entry: skipped, refused, or waiting for a
  person. An event booked earlier is never counted here, even after you change the template to skip its
  kind (its outcome then names the earlier entry).
- `differenceMinor`: booked minus expected.
- `unexplainedMinor`: booked plus bank payouts plus not booked, minus expected. It is 0 when every Rappen
  of the file is accounted for. Anything else points at an event booked with other figures
  (`event_amended`), a reversing entry, or a clearing account changed since.

Once the bank lines for the payouts are booked (a Buchungsregel that books the bank line against the
clearing account does this), the clearing account carries booked plus bank payouts, which is the
expected change minus what the import left off: what the processor still holds, usually a reserve.
